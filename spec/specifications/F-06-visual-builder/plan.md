# Implementation Plan — Visual builder: the Map tab, flow tabs, gates and checks, custom agents (F-06)

Each task is **one implement → review → test → commit cycle** and produces exactly one commit. Rules for tasks:

- **Small:** about 50–200 changed lines, one clear purpose.
- **Green:** the repository builds and all tests pass after the task.
- **Tests travel with the code:** in the same task.
- **Ordered:** a task never depends on a later task.
- **Traceable:** each task names the acceptance criteria it covers.

## Rationale

- **Decision record first (T001).** The removal of `review`, the view-model boundary and the reuse of `analyzeStructure` are decisions. `general.md` requires them in the architecture before code depends on them.
- **Core before web (T002 to T003).** The web builder types its state on the pipeline model, so the model must be right first. `review` leaves the model in T002; the default data follows in T003, so the default parses with the new union.
- **The view-model before the components (T004 to T015).** The logic is pure and is tested with Vitest, as architecture §5 asks for `source/apps/web`. The components (T016 to T019) only bind it. No DOM test library is in the MVP, so the components have no test of their own; their behaviour is covered by the view-model tests and the `[device]` checks.
- **Entry checks and live marks are separate (T008, T011, T013).** Entry checks refuse a value the model cannot hold (an id, a number, a body over its cap). Live marks show a structure problem and never refuse an edit (AC-039). The parser refuses structure, so the builder does not call it on each edit; the marks use `analyzeStructure`, the rule set F-04 already built. That answers the open point of F-06's specification: the rule module exists, so no rule module is built in F-06.
- **Marks use the F-04 analyzer (T013).** `analyzeStructure` already returns the structural findings (cycles, wiring, unbounded retries) with a subject path. The mark maps the path to the item. One rule has one implementation (AC-038).
- **Order of the flat removal (T020 to T021).** F-05's plan keeps the flat builder at step 3 until F-06 and deletes the flat brief in its T005 to T013. The flat model is used by the flat brief (`source/apps/web/src/brief/to-config.ts`) until F-05 removes it. So T020 needs F-05 T001 to T015 committed. Until then, T001 to T019 run, since they add files and do not touch the flat builder's mount point. T021 deletes only what no consumer imports; the grep is part of the task.
- **Prerequisite.** F-05 T016 (step 3 hosts this builder) needs F-06 complete. F-06 T020 needs F-05 T001 to T015. Build F-05 T001 to T015, then F-06 T001 to T022, then F-05 T016.
- **No device criteria in the view-model tasks.** AC-005 (drag gesture) and AC-045 (reload) are `[device]`; they are on the checklist of the verify step.
