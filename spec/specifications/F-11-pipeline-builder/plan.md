# Implementation Plan — Pipeline builder (UI only) (F-11)

Each task is **one implement → review → test → commit cycle** and produces exactly one commit. Rules for tasks:

- **Small:** about 50–200 changed lines, one clear purpose.
- **Green:** the repository builds and all tests pass after the task.
- **Tests travel with the code:** in the same task.
- **Ordered:** a task never depends on a later task.
- **Traceable:** each task names the acceptance criteria it covers.

## Open points for the approval (decide before Build)

Both were decided by the user at approval (2026-11-17), with the recommended options:

- Flow name is free text and unique; the id is file-safe and fixed at creation. AC-029 is reworded in `stories.md` to match.
- A flow that already has an arrow refuses a new one, with the reason (T003).

1. **Flow name and id (AC-029, screens 04 and 07).** A flow has a free-text `name` (`Specify`) and a file-safe `id` (`specify`), and the generated command file is named from the id (`architecture.md` §6, decision 33; `ui.md` §4). AC-029 asks for the name to be file-safe. **Recommended:** the Name field edits `name` (non-blank, unique among the flows' names, refusal with the reason); the id is file-safe and fixed at creation (`flow-2`, shown as "Generates .claude/commands/flow-2.md"); AC-029 is reworded to say so. Alternative: the Name field edits the id, which renames the file and must rewrite every link to it.
2. **One outgoing arrow per flow.** A flow holds one `connectedTo` (decision 33). **Recommended:** Connect to next flow, or a drag from the flow, is refused on a flow that already has an arrow, with the reason; the user removes the arrow first. Alternative: the new arrow replaces the old one after a confirmation.

## Rationale

- **Order.** T001 to T010 are pure logic in `source/apps/web/src/builder/` with no React, so each is tested with table-driven Vitest tests (`qa.md`). They read the approved model (`source/packages/core`, unchanged) and the analyzer and parser that `core` already exports, so no core change is needed: `architecture.md` §6 decision 24 puts the builder's rules in the web view-model and the marks in the analyzer. T001 comes first because every later task reads the tab order and the box list from it. T002 (layout) and T003 to T008 (edits) depend only on T001. T009 (marks) and T010 (panel content) depend on the model and the analyzer.
- **State before UI.** T011 adds the pipeline to the wizard state after all the edit functions exist, so the state holds the same shape they produce. T012 to T016 are the components, in the order of the screens: the shell and tabs first (T012), the panels and toolbox (T013), then the canvas (T014), the marks (T015) and the button paths and confirmations (T016). T017 wires the step into the wizard and the app last, after the components. T018 documents the decisions once the behaviour is in place.
- **Libraries.** `@xyflow/react` 12.12.1 and `@mui/material` 9.5.0 are already in `source/apps/web/package.json` and approved in `architecture.md` §5. No new dependency. Drag and drop is done with the React Flow pointer events and `onConnect`, not with an HTML5 drag library.
- **Testing.** T001 to T010 and T016's logic are pure and need no DOM. The component tests (T012, T013, T015, T016) use `@testing-library/react` with jsdom, as `RuleBlocks.dom.test.tsx` does. React Flow itself needs a browser layout: T014's pointer gestures (AC-011, AC-012, AC-022) and the layout of AC-024 are `[device]`, checked on screen at Verify, with the drawing logic (edge positions, gate placement, the repoint and gate decisions) tested in T002 to T006.
- **Refusals come from the parser.** T007 uses `parseProjectConfig` (decision 33 and the F-02 parser) so the messages a field shows are the same messages the Analyze step returns later. A candidate pipeline is built and parsed; only problems at the edited field's path refuse the edit.
- **Marks come from the analyzer.** T009 calls `pipeline.analyzeStructure` and maps each finding's path (`pipeline.flows[i]`, `pipeline.flows[i].connectedTo`, `pipeline.flows`, a block path) to a box, an arrow or "Not on a drawn item". No rule is copied into the builder (AC-039).
- **Rule tags need rules.** The analyzer warns about rule tags that name no rule. The config passed to it needs the rule list of step 2 (F-10), so T009 builds `ProjectConfig.rules` from the step 2 rule blocks with the F-10 rule-id function (`technical.ts`). Without this every rule tag would be flagged.
- **Scope.** No Analyze button and no generation (F-13, F-14). No flow tab content (F-12). No storage (decision 13).
