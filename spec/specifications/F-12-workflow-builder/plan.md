# Implementation Plan — Workflow builder (F-12)

Written from the approved stories (`stories.md`, 9 stories, 53 criteria, approved 2026-11-23) and the approved screens (`spec/design/features/F-12-workflow-builder/`, the six screens 01 to 06 of 2026-11-19, approved 2026-11-23). Where the screens and the stories differ, the plan follows the stories and lists the difference under "Differences from the approved screens" in the rationale, for the user to confirm at plan approval. States that the stories require and no approved screen draws are built to the stories, in the style of the screens.

Each task is **one implement → review → test → commit cycle** and produces exactly one commit. Rules for tasks:

- **Small:** about 50–200 changed lines, one clear purpose.
- **Green:** the repository builds and all tests pass after the task.
- **Tests travel with the code:** in the same task.
- **Ordered:** a task never depends on a later task.
- **Traceable:** each task names the acceptance criteria it covers.

## Rationale

- **Order:** pure logic first (T001–T013), so each builder rule is a Vitest test with no DOM before any component uses it. The rules come in dependency order: ids and layout (T001–T002), then the arrows (T003), the link rules that use the layout order (T004), the arrow repoint and removal (T005), the field edits through the parser (T006–T009), delete (T010), marks (T011), selection (T012), then the flow tab state (T013). Then the components from the outside in: toolbox (T014), canvas (T015–T016), panels (T017–T021), marks in the UI (T022), wiring on step 3 (T023). Docs (T024) come last, as in F-11.
- **Reuse, not rewrite:** the field rules go through `parseProjectConfig` (core), as F-11 does, so refusal wording comes from the parser. The structure findings come from `analyzeStructure` (core); block findings use the path `pipeline.flows.<n>.blocks.<m>` already emitted by core. The pipeline panel, RowEditors, ConfirmDialog, ConnectionPanel, MessageBand and ErrorPanel are reused from F-11.
- **Core untouched:** `parseProjectConfig`, `analyzeStructure` and `defaultPipeline` are exported by core already (F-02, F-03). No core change is planned, except the Agent body rule in T006 and the reads and writes check in T025 (Amendments 2026-11-23). The End count rule in the analyzer (`start-end.ts`) already reads "at least one End", so no parser change is needed for AC-038.
- **Representation of an open route (decided here, not in the stories):** an empty true output is `to: ''` (shown "No arrow yet"); an empty false output is `{ stop: true }` (shown "Stop the flow and ask the user"); a new block has blank fields, so the analyzer reports it and the edit paths refuse only the field they change, as F-11 does for a new flow.
- **Device checks (Verify):** AC-007 (shapes readable), AC-008 (arrow styles and labels) and AC-012 (drag gesture) are `[device]` and go into the Verify checklist.
- **Size:** the block panel (T017–T021) is the largest part. Each task has one panel section, so each stays near the size guard. A task that grows past 400 changed lines stops the pipeline (Amendment).
- **Dependencies:** F-11 is complete (all phases ✅). No new library is needed; `@xyflow/react` is already approved and used by F-11.

### Differences from the approved screens (for the user to confirm at plan approval)

1. **Link icon.** Screen 01 draws a Link icon in the toolbox. The stories (AC-001, AC-012) have no Link tool; arrows are drawn by dragging. The plan follows the stories (T014).
2. **Reads, Writes and Rule tags.** The Agent panel of screens 02 and 06 has Name, Description, Arguments, Model, Tools and Body only. The stories require Reads, Writes and Rule tags (AC-022, AC-026, AC-027). The plan adds them to the Agent panel (T018).
3. **False route.** Screens 03 and 04 draw the false route as a dropdown. The stories (AC-032) make it text, set by the arrow. The plan follows the stories (T019).
4. **Name clash wording.** Screen 06 reads "planner is taken by another agent." The stories (AC-023) read "Another Agent already has this name." The plan follows the stories (T017).
5. **Delete confirmation wording.** Screen 05 reads "Delete the planner block? … Its arrows are removed too." The stories (AC-039) require the block's name and the arrow count. The plan follows the stories and keeps the screen's layout (T021).
6. **States with no approved screen.** The Start panel, the arrow panel for blocks, the link and round-limit refusals, the empty flow, the structure marks, the Start and last End delete refusals and the no-artifacts End. The stories require them; the plan builds them to the stories in the screens' style (T017–T022).
7. **Draft questions on the screens.** Screen 03 asks what a false pre-check does (question 9), screen 04 asks the range and default of the round limit (question 10), and screen 01 asks whether the artifact in an End is its label or its id (question 5). The stories answer them: a false pre-check stops the flow (AC-020, AC-032; `pipeline-schema.md` §6), the round limit is 1 to 5 (AC-033), and the End names an artifact by its label (AC-036).
