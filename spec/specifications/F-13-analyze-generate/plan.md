# Implementation Plan — Analyze and generate step (UI only) (F-13)

Written from the approved stories (`stories.md`, 5 stories, 31 criteria, approved 2026-11-24) and the approved screens (`spec/design/features/F-13-analyze-generate/`, 11 screens, approved 2026-11-24). The reviews were skipped at the owner's request, so the screens are the approved ones as drawn.

Each task is **one implement → review → test → commit cycle** and produces exactly one commit. Rules for tasks:

- **Small:** about 50–200 changed lines, one clear purpose.
- **Green:** the repository builds and all tests pass after the task.
- **Tests travel with the code:** in the same task.
- **Ordered:** a task never depends on a later task.
- **Traceable:** each task names the acceptance criteria it covers.

## Rationale

**Order.** The logic that the screens depend on is pure and tested first (T001 to T007): the configuration, the analysis state, the reasons, the request, the replies, the templates and the tree. The components (T008 to T010) take their values from that logic, the actions (T011, T012) join the components to the request, and the wiring (T013) puts the step into the wizard. The docs (T014) come last, after the behaviour exists.

**Decisions taken in this plan.**
1. **The preview uses `listFiles`, not `planGeneration`.** `planGeneration` refuses a configuration with a blocker and lists no file. Screens 03 and 11 show the tree beside a blocker, so the preview lists the files from `listFiles`, which is the same file order the generator uses.
2. **Rule blocks with an invalid id get no file in the preview.** The analysis reports them (a blocker or warning); their file name is not a file-safe path, so the tree leaves them out rather than throw.
3. **`Accept: application/json` on every request.** The Vite dev server answers a `fetch` with `Accept: */*` and an unknown path with its HTML page and status 200. With the header sent, the missing endpoint gives a real 404, which the stories and AC-031 depend on.
4. **Out of date means a different configuration key.** The result stores the JSON of the configuration it ran on; any change to a brief field, a rule block or the pipeline gives a different key, so no flag has to be kept in step with each field.
5. **The analysis state lives in the step.** It is held in memory and is lost when the user leaves step 4, which is the same as the values' refresh behaviour in the footer note. A new Analyze after returning starts from a fresh state.
6. **The 422 body shape is an assumption.** The docs say a 422 lists `<path>: <reason>` problems but do not name the field. T005 reads `problems: string[]` and falls back to the error text when it is missing. F-14 defines the body; if it differs, the change is in T005 only.
7. **No new libraries.** The file tree uses core's `listFiles`; the dialog uses Material UI, already in use. Nothing is added to `architecture.md` §5.

**Constraints that shape the tasks.** `source/packages/core` and `source/apps/api` are not changed (F-13 is web only). The web styling rules apply to every component: style getters take the theme, no inline `sx` or `style`, colours from `theme.ts` only (T008, T009, T010). The memory-only rule applies to the wizard source (no storage, no console; T013). Tests use fakes and fixed inputs: no test calls the network or the wall clock (T004, T011, T012).
