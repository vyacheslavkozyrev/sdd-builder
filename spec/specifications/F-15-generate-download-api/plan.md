# Implementation Plan — Generate and Download API (F-15)

Each task is **one implement → review → test → commit cycle** and produces exactly one commit. Rules for tasks:

- **Small:** about 50–200 changed lines, one clear purpose.
- **Green:** the repository builds and all tests pass after the task.
- **Tests travel with the code:** in the same task.
- **Ordered:** a task never depends on a later task.
- **Traceable:** each task names the acceptance criteria it covers.

Paths are relative to the repository root. API tests live in `source/apps/api/test/`, use Hono's in-memory `app.request` (no network port) and fakes for the model. Each test name carries `F-15 AC-0xx`. No test calls the real provider, the network or the wall clock. No test reads the real environment: settings are tested with plain objects.

## Rationale

- **Settings and loader first (T001, T002).** The model name and the templates are inputs to everything else; both are tested without a server.
- **Pure pieces before the service (T003 to T006).** Reply parsing, the prompt, the call and the zip each have one purpose and a test that uses fakes; the service then only sequences them.
- **Service before route (T007, then T008).** The route maps results to status codes; the status rules are tested through the route after the service is tested directly.
- **Wiring last (T009).** It is the only place the key, the model and the templates meet; the entry point stays out of every test.
- **Docs last (T010).** It records the settled behaviour in `architecture.md` once the code has it.
- **F-14 test amended in T008.** The F-14 route test asserted that `POST /generate` gives 404, which F-15 changes. Its case is moved to the new route test in the same task, so the suite stays green.
- **Core.** No change to `source/packages/core`: `planGeneration`, `checkReply`, `configProblems`, `GenerationError` and `GenerationTemplates` already exist.
- **Libraries.** None added. `jszip` 3.10.2 and `@anthropic-ai/sdk` are already dependencies of `source/apps/api` (`architecture.md` §5).

**Interpretations** (choices made here; the owner may change them):

- A generation reply is parsed strictly: the whole text is one JSON object, with no code fence and no leading text, as the review reply is.
- A reply whose stop reason is `max_tokens` is a bad reply and gets the one retry, since its JSON cannot be whole.
- The checks run in this order: body (400), configuration refusal (422), model not configured (503), then the model call. A refused configuration with no key gets 422 (AC-009).
- The prompt is fixed in the API (the review prompt pattern); core only checks the reply.
- Templates are read once at startup, not per request, so a missing template fails the server start rather than one request.
- Zip entries are the planned files only, with no directory entries (`createFolders: false`).
- The 422 body names the refusal and lists the blockers; the 502 bad-reply body lists paths and messages only (AC-019).
- The generator model default `claude-opus-5-5` is my choice (the Specify answer gave the setting, not the value); it is recorded in the stories.
